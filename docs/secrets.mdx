An entry is a secret when it was written as one (`secret: true`), or when its value is a `vault://`
reference. Secret values are **never stored in plain text**.

## Encrypted at rest

Secret values are sealed by the **Agora crypto kit**, the same implementation every `@adonis-agora`
lib carries verbatim (`src/crypto-kit/`). No key handling of our own:

- purpose `config:secrets` (one APP_KEY never yields the same key for another lib);
- the kit is built on **AdonisJS encryption** (`@adonisjs/core/encryption`, `@boringnode/encryption`):
  AES-256-GCM, key rotation, purpose; the kit binds the AAD as authenticated data;
- **AAD = app / environment / key**, so a ciphertext cannot be moved to another entry (or another
  app/environment) without failing to open;
- format `agora:v1:<adonis ciphertext>` (or the KMS envelope); a dump has ciphertext only.

Nothing to configure: the default keyring is one key with id `app` derived from `APP_KEY`.

```ts
// optional: key rotation or a KMS key
defineConfig({
  topology: 'control-plane',
  verifyTenant,
  crypto: {
    keys: [
      { id: '2026-11', secret: env.get('APP_KEY_2026_11') },
      { id: 'app', secret: env.get('APP_KEY') }, // still opens old values
    ],
    active: '2026-11',
  },
})
```

For envelope encryption, `crypto.kms` is a `KmsAdapter` (`{ wrap, unwrap }`): every value carries a
fresh data key wrapped by it. The kit ships an in-memory adapter for tests and documents the real
cloud adapters.

### Rotating

1. Add the new key first (and make it `active` when you use ids); deploy. Existing values still open
   (every key in `keys` can decrypt). The common shape is `keys: [nova, antiga]`, first key seals.
2. Preview: `node ace config:crypto:reseal --dry-run`.
3. Run `node ace config:crypto:reseal` — it walks **every version and the audit before/after** and
   re-seals values whose `sealedStatus` is not `active`.
4. `node ace agora:doctor --deep` shows no `retired`/`legacy`/`unreadable` values; then drop the old
   key.

`keys` may also be a plain list (`keys: [nova, antiga]`); the first one seals. `active` only makes
sense with the `{ id, secret }` form.

A value that cannot be re-sealed (missing key, tampering) is left untouched, counted as `failed`,
and makes the command exit 1 — never silently lost.

`node ace agora:doctor` also reports `config.crypto`: `warn` for retired/legacy values (run the
reseal), `error` for a value nothing can open.

The tenant's snapshot is a copy of what its token may read, written on the app host (`0600`). Give a
tenant `config:secrets:read` only when it truly needs secret values at boot; otherwise the snapshot
never holds them.

## Sealed to an app

A symmetric secret is readable by the control plane (it holds the key). For a value that only one
tenant app may ever read, **seal it to that app's public key**: the control plane writes the
ciphertext and can never open it again.

Every tenant app has an X25519 key pair:

- the **private key stays in the app**, sealed at rest with the same crypto kit (APP_KEY), in
  `storage/config-tenant-key.json` (mode `0600`, `tenant.keyPath` to move it);
- the **public key is registered** with the control plane on first connect (`PUT /v1/keys`) and can
  be inspected/rotated from the app.

```sh
node ace config:tenant:key                 # show the key, its kid, and what is sealed to it
node ace config:tenant:key --rotate        # new key, publish it, re-seal the old values
node ace config:tenant:key --reseal        # only re-seal to the active key (--dry-run to count)
node ace config:tenant:key --application=shop   # on a server: list the app's public keys
```

Then write the entry as sealed:

```sh
node ace config:entry:set stripe.secret sk_live_123 --sealed --application=shop
```

In the console the same thing is the **seal for <app>** checkbox. The value is sealed with
`sealTo` (the kit's ephemeral X25519 + HKDF + AES-256-GCM construction) and bound to its place with
the same AAD (`config:<app>:<environment>:<key>`), so it cannot be moved to another entry either.

What each side sees:

| Where | Sees |
| --- | --- |
| control plane store / a database dump | `agora:pk1:<kid>:…` ciphertext only; no code path opens it |
| console and CLI | **sealed for shop**; no reveal button, no `config:secrets:read` path |
| the target app (`sealedTo.app`) | the plaintext, opened at boot and on reload with its private key |
| any other app | nothing: the `kid` has no matching private key, so the entry stays masked |
| the snapshot file | the ciphertext the server sent, never the opened value |

A token still needs `config:read`; `config:secrets:read` only decides whether the server sends the
ciphertext at all (without it the entry is masked like any other secret). The value never lands in
`process.env` on the server, in `config:env`, or in the audit trail in clear.

**Rotation.** `--rotate` creates a new key, keeps the retired private key (so old values still open),
publishes the new public key and re-seals every value sealed to the old one; it is the only side that
can, because only it can decrypt. `node ace agora:doctor --deep` reports the key state
(`config.tenant-key`): a missing keyring, an unregistered key, sealed values still on a retired key,
or values that do not open.

An app without `APP_KEY` cannot hold a private key: sealed values stay masked and the doctor warns.
Set `tenant.keyPath: false` only for an app that never receives sealed secrets.

## Vault references

A value can be a reference resolved when it is read:

```ts
{ key: 'stripe.secret', value: 'vault://aws/prod/streaming#stripe_key', secret: true }
```

```ts title="config/config.ts (the server)"
defineConfig({
  topology: 'control-plane',
  verifyTenant,
  vault: {
    async resolve({ provider, path, field }) {
      // authkit's vault packages, AWS Secrets Manager, HashiCorp Vault, …
      return mySecretManager.read(`${provider}:${path}`, field)
    },
  },
})
```

The reference is stored; the resolved value is not. A reference that cannot be resolved is served
`masked: true` and logged — never as a wrong or empty value.

## Who may read a secret

| Caller | Needs | Gets |
| --- | --- | --- |
| a tenant with `config:read` | — | `masked: true`, no `value`, the `vault` reference still visible |
| a tenant with `config:secrets:read` | `config:read` too | the decrypted value, or the vault-resolved value |
| the console | its `authorize` gate; an explicit reveal, audited | the value |
| the CLI / an MCP read | `--secrets` on `get`/`env`/`pull`, or `revealSecrets` for MCP; audited per key | the value |

The masked entry carries no `value` key at all, so a client cannot confuse "you may not read this"
with "this is empty".

## The audit trail

```json
{
  "actor": "ann@example.com",
  "action": "reveal",
  "key": "stripe.secret",
  "version": 7,
  "at": "2026-11-14T18:00:00.000Z"
}
```

`set` and `unset` rows keep before/after entries, themselves sealed. A reveal row records who read
which secret at which version.
